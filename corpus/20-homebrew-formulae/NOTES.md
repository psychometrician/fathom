## Why this one, and why it is deliberately unexciting

**`design/implementation.md` sets the rule this choice has to obey**: a document
picked to break the newest constant is guaranteed to find something and
therefore cannot measure convergence. Files 17, 18 and 19 closed the gate
precisely because they were chosen as ordinary, and that rule is part of the
result.

So this was chosen for being **ordinary and tool-written**, which is also what
`corpus/README.md` asks for — *prefer documents no API has tidied*, weighted
toward things written by a tool rather than served by an endpoint. A package
index is about as everyday as machine-written JSON gets.

It takes a second **scale** reading as a side effect, at roughly the size of
`14-nyc-311`. That is a by-product, not the reason.

### Prediction 7 is the interesting failure

225 lines, not 120. **But the claim it was testing survives, and the line count
was the wrong instrument for it**: the description is **16,515 bytes against
29,066,917 of input — 0.053%.** That is the smallest ratio in the corpus. A line
count is a budget for a reader; the ratio is the claim. Predicting the first
and calling it a test of the second was my error, not the probe's.

### Prediction 9 was wrong in the direction that should be embarrassing

I predicted the prototype would need over a gigabyte, from the 18.8× multiplier
`04-gharchive` gave. It needed **293 MB — 9.4×**. `design/implementation.md`
already says, twice, that the multiplier tracks the record shape rather than
the format and that quoting it as a property of the tool is a mistake. **I quoted
it anyway, on the same day I wrote that warning into a commit message.**

## What this file disconfirmed

**Two new defects, and they are the ninth held-out run in ten to find one.**
Recorded, not repaired — rule 5.

> **REPAIRED later the same day, at `61af6458…`, with the author's
> authorisation.** The scorecard above is left exactly as it was scored: it is
> the record of what `dcd6ec8b…` did on an unseen document, and rewriting it
> would destroy the only thing a cold run is for.
>
> **The two defects were one.** The guard added for defect 17 returns a verdict
> that `containers()` also folds on, so declining to *name* `$[].variations`'
> keys stopped its siblings *folding* — thirteen platform sites, each too small
> for that same guard to fire on. After the repair this file's report is **176
> lines, not 225**, and its keys-as-data goes **23 → 4**. Prediction 7 is still
> wrong, and less wrong; the 0.053% ratio it should have measured is unchanged.
>
> `FINDINGS.md` has the measurement, including the nine candidate signals that
> failed and the proof that `VOCAB_GROWTH`'s justifying gap is a copy-count
> artifact.

**Defect 22 — thirteen false positives, in the report's largest block.** The
probe lists `$[].variations.arm64_big_sur` and twelve siblings under **KEYS THAT
ARE DATA**. They are not data. Their keys are `build_dependencies`,
`dependencies`, `head_dependencies`, `requirements`, `patches`,
`conflicts_with`, `caveats`, `keg_only` — **a closed vocabulary of eleven field
names, the same names the formula itself carries.** A `variations` block is an
override table: the platform is the data, and the keys inside it are the fields
being overridden.

> **The `VOCAB_GROWTH` guard exists for exactly this and does not fire, and the
> reason is precise.** It measures keys ÷ copies, fitted on `engines` at 0.005
> and Stripe's `paths` at 0.007 against `scripts` at 0.030. Here it is **11 ÷ 89
> = 0.124**, four times above the threshold — not because the vocabulary is
> open, but because there are only 89 copies. **The measure conflates *a closed
> vocabulary* with *few copies*, and this document separates them for the first
> time.**

**Defect 23 — the summary line states a reason that is false.** The report says
*"could not call 15 small single-copy objects"*, and one of the fifteen is
`$[].bottle.stable.files`, which has **8,531 copies**. The sentence was written
when `undecided` had one cause; the `VOCAB_GROWTH` branch added at `a9e17af0…`
gave it a second and nobody revisited the label. Prediction 3 was right about
the verdict and the verdict came with a lie attached.

### What it confirmed

**The port is faithful on a document neither implementation had seen.**
Byte-identical, 225 lines, including both defects above — which is the contract
working: a port that had quietly "fixed" the false positives would have been
unverifiable.

### Seven tools, two languages, identical numbers on question 11

**65 URL paths naively, 48 strictly** — jq, jqr, ijson, glom, pydash, purrr and

### What the running caught that reading would not — eight this time

- **purrr's path walk said 1,181 where six tools say 1,132.** One line: it
  registered the `[]` child path *before* iterating, so an array with no
  elements still contributed one. This document holds **141,444 empty arrays**
  and 49 paths — 4.3% — existed only because of them. The Python walks put the
  same assignment inside the loop and were right by accident of style.
- **pandas `errors="ignore"` does NOT cover a missing `record_path`.** It raises.
  The obvious fix — keep only formulae whose patches all carry `resolves` —
  runs clean, warns about nothing and returns **409 rows against a true 557**.
- **glom's `Coalesce` does not collapse absent-vs-null**, which I predicted it
  would; and **pydash's `get` does not either**, which I then predicted was a
  difference between them. They print identical answers. Entry 15's trap is the
  **deeper path**, not the top level.
- **purrr's `pluck(.default=)` DOES collapse them**, so the corpus has three
  defaulting verbs and two behaviours, and entry 15's "pydash and purrr share
  the blind spot" is too strong.
- **rrapply's melt KEEPS nulls** — 178,188 of them — where I predicted it drops
  them. That is why it answers question 4 correctly and sits with the walkers.
- **`bottle.stable.files.<platform>` is at L5, not L4**, because L1 is the record
  index — the identical mistake entry 17 recorded against this melt layout.
- **jmespath's `keys()` raises on a null and kills the whole query**, because
  five formulae have no `bottle`. The mirror of pandas' `record_path` raise.
- **`desc` is a SQL reserved word**, so `SELECT name, desc, homepage` is a
  parse error in DuckDB on a document whose records have a field called `desc`.
