## Why this one, and why it is deliberately unexciting

**The counter is at 1 of 3.** Files 21 and 22 were both **paginated API list
responses** — an envelope around one array — and were chosen to differ in
regularity rather than in shape. **A third of the same shape would test less
than it looks like it does.**

This one was chosen for a **structural gap**: every document in the corpus is
one array of records, a wrapper around one array, or a map keyed by name. **None
is one object holding SEVERAL DIFFERENT collections side by side.** That is an
everyday shape — it is what a dashboard endpoint returns — and the corpus has
never asked the probe to describe one.

> **What I deliberately did NOT do is pick a document I expect to stress
> `folds()`.** OSM Overpass, `caniuse-db` and CloudFormation were all considered
> and rejected for exactly that: their headline property is an open vocabulary
> used as keys, and a document chosen knowing it attacks the newest rule cannot
> measure convergence even if it is otherwise ordinary. **I expect keys-as-data
> to be zero here, and prediction 5 says so, so the reader can check that the
> choice was not stacked.**

**Small on purpose, and the same limitation as file 22**: this says nothing
about scale.

## What this file disconfirmed

**Defect 25 — the description says the same thing four times.** Recorded, not
repaired, per rule 5.

Of **11 object sites, only 5 are distinct key-sets**. The 23-field crate record
appears under `new_crates`, `most_downloaded`, `most_recently_downloaded` and
`just_updated`; its 6-field `links` does the same. **The probe prints both field
lists four times each**, so 8 of 11 sites — and roughly 32 of the report's 49
lines — are reprints.

**`fold_recursion()` already knows that identical key-sets are one shape**, and
merges them when one is reachable from the other; the reachability guard is
defect 1's repair. **Sibling collections of one record type are not recursion,
so nothing merges them**, and the probe has no way to say *same shape as
`$.new_crates[]`*.

### It is corpus-wide, and on four files it is eating the shape cap

Measured across all 23 documents, counting only key-sets of three fields or
more, and then counting what the reports actually print:

## Grading

**Graded in all thirteen tools on 2026-08-11.** The probe was not run and not
unfrozen.

### 1. "Same shape" and "same schema" are different questions, and this document separates them

The probe folds on KEY-SETS and prints `same shape as $.new_crates[]` — defect
25's repair. **Three type-inferring tools independently disagree**, and all four
answers are correct:

| | verdict | why |
|---|---|---|
| the probe, jq, jqr, ijson, glom, pydash, purrr | **one shape** | one key-set over all 40 records |
| polars | **three schemas** | `recent_downloads` Null vs Int64 |
| DuckDB | **three types** | `recent_downloads` JSON vs BIGINT |
| jsonlite | **three type vectors** | `recent_downloads` logical vs integer |

The cause is one column: **`recent_downloads` is null on all ten `new_crates`**,
and `documentation` on all ten `just_updated`, so a value-typing tool infers the
null type there and a real one elsewhere. **A key-set is a property of the keys;
a schema is a property of the values, and a column that is empty in one
collection has no value to type.**

### 2. Concatenating the four fails FIVE ways, from that one cause

| | |
|---|---|
| pandas `concat` | **succeeds silently**, and yields `documentation` as **str 16, float 14, NoneType 10** — a column missing in two incompatible ways |
| polars `concat` | **RAISES**: `type Int64 is incompatible with expected type Null` |
| DuckDB `UNION ALL` | **view builds, `count(*)` returns 40, and EVERY FIELD ACCESS RAISES** — `count(DISTINCT crate.id)` errors naming a URL in `documentation`, a column you never asked for |
| R `rbind` | **RAISES on ROW NAMES**, before it ever looks at a type |
| `dplyr::bind_rows` | **succeeds silently**, coercing logical NA into integer |

**DuckDB's is the worst**: forty rows and no readable columns looks like it
worked until the second query. **R holds two of the five by itself.**

### 3. The overlap, which no tool reports and the probe does not either

**40 crate rows hold 33 DISTINCT crates.** `bitflags`, `getrandom`, `hashbrown`,
`libc`, `rand`, `rand_core` and `syn` each appear in two collections.

> Concatenating the four is the obvious move *once you know they share a shape*,
> and it silently double-counts seven crates. The probe prices each list at ten
> rows and says the shapes are identical — **both true, and neither is "the
> contents overlap"**. This is the clearest case in the corpus of a question the
> probe does not ask.

### 4. tidyjson's rule, third test, and the prediction was exact

Six fields bear a null; **three are null on all 40** — `categories`, `keywords`,
`versions`. A field that is never anything but null has ONE type.
**Predicted three mistyped fields, measured three**: `documentation`, `homepage`,
`recent_downloads`. Entry 20 narrowed the rule to *sometimes-null* fields, entry
22 confirmed it one level down, and **this is the first document where the two
sets differ in size** — six null-bearing fields, three mistypable.

### 5. What the running caught

- **`enter_object(k)` with a VARIABLE returns zero rows and raises nothing.**
  tidyjson uses non-standard evaluation, so a variable is taken as a literal key
  name. The first draft of `try-tidyjson.R` printed **0 crate rows, 0 varying
  fields and 0 distinct key-sets**, and every one of those zeros looked like a
  finding. `enter_object(!!k)` gives 10.
  > **Third instance of the same class**: entry 20 found a `tbl_json` has no
  > `json` column, entry 22 found `distinct()` on one *errors*, and here
  > `mutate()` silently loses a column and `enter_object` silently returns
  > nothing. **A tidyjson table looks like a tibble and is not one, and the
  > failure mode differs by verb.**
- **DuckDB's `UNION ALL` view had to be abandoned entirely** for a union of
  JSON TEXT, because every field access on the struct raised. The working route
  leaves the relational types behind — and then double-counts the seven
  overlapping crates exactly as pandas did.
- **R has no implicit string concatenation across lines**, and jq's `\(...)`
  interpolation reached through an R string literal comes out as a literal
  backslash. Both killed a draft of `try-jqr.R`.
- **jqr returns one character element per jq OUTPUT**, so an array comes back as
  a single string and `length()` is 1. `.[]` fixes it.

### 6. `bind`'s mechanism confirmed by its limiting case

**10 x 27 at 0.0% NA** — the first `bind` in the corpus with **no NA at all**.

| 14 | 17 | 18 | 20 | 21 | 22 | **23** |
|---|---|---|---|---|---|---|
| 20,000 x 50 | 36 cols, 64% | 100 x 37,006, 98.1% | 8,536 x 3,415, 98.3% | 1,000 x 8,439, 97.7% | 100 x 213, 21.8% | **10 x 27, 0.0%** |

Entry 22 pinned the mechanism — a column per (position, field) pair. **This
document has no array below the records at all, and the table comes out dense.**
Predicted 29 (23 fields + 6 `links` children); measured 27, because two fields
are null on all ten of that collection and contribute no column.

### 7. Where the tools agree

**Seven tools report 11 distinct URL paths folding to 3** — jq, jqr, ijson, glom,
pydash, purrr, rrapply. **The four-in-one shape inflates the path count four
times over**, exactly as it inflated the record-shape listing before defect 25's
repair. **The probe folds the SHAPES and does not fold the PATHS.**

**rrapply's melt is the closest any tool comes to volunteering defect 25's
answer**: L1 is the collection and L3 the field name, so one `table(L3, L1)`
shows the four sharing a vocabulary — out of the default representation, not a
comparison you had to think to write. **ijson is second**: four sibling prefix
families with identical tails, visible in the output itself. **ijson is also the
only tool that cannot see the overlap at all**, since noticing a repeated `id`
means keeping a set — the one thing a streaming parser exists not to do.

**Question 10 has NO TARGET.** There is no array below the collections; `links`
is an object of six fields. **First corpus document where that is true.**

**Question 7 has three answers again**: `num_crates` 314,344, `num_downloads`
394,080,457,094, and 40 rows here of which 33 are distinct.

## The fourteenth tool, 2026-08-11 — `try-tidyr.R`

**A rectangling tool lands in the type-inferring group, because a column must
have a type.** tidyr never asks for a schema and gets one anyway, so it joins
polars, DuckDB and jsonlite rather than the key-set group — and the four
collections' columns then disagree **in two places and in opposite directions**:

| | new | most_dl | most_rec | just |
|---|---|---|---|---|
| `recent_downloads` | **logical** | integer | integer | integer |
| `documentation` | character | character | character | **logical** |

**AND THE THRESHOLD IS MEASURED, which no other tool here did.**
`documentation` is null on **EIGHT of ten** `new_crates` and still types
character; null on **TEN of ten** `just_updated` and types logical.
**Total absence flips it; an 80% null rate does not.**

**The prediction I got wrong, and its correction is worth more.** I expected
`unnest_longer` on the empty `keywords` to drop every row. **It drops none** —
because **five of the 23 crate fields are not list-columns at all**. Total
absence typed them logical too:

| in the JSON | column class |
|---|---|
| `badges` — a real empty **ARRAY** | `logical` |
| `yanked` — a real **BOOLEAN** | `logical` |

> **The field's KIND is erased, not just its value.** An array field and a
> boolean field are the same type in the finished frame and nothing
> distinguishes them.

`bind_rows` coerces both mismatched columns **correctly and silently** —
`integer` and `character`, no warning. **The silence is the defect, not the
result.** And the flat table is **40 x 29 with ZERO list-columns**, which wears
the face of a clean flatten: it is fully rectangular only because every nested
field in every crate was empty.
