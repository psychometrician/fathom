## Why this one, and why it is deliberately unexciting

**The counter is at 1 of 3, and this file is chosen for SIZE.** Files 22, 23 and
24 are 476 KB, 41 KB and 27 KB, so **three consecutive quiet-ish results came
from documents with few chances to speak** — which is a real weakness in them,
stated in file 24's notes before this one was picked. Files 21–24 varied
regularity, shape and producer; **size is the axis left, and it is the one that
has found the most defects.**

Chosen also because a **scientific event catalogue** is a producer the corpus
does not have, and because it is about as ordinary as public data gets.

> **The shape overlap with `03-natural-earth` is real and is stated rather than
> hidden.** Both are GeoJSON `FeatureCollection`s. **The interiors are
> opposites**: Natural Earth is ~250 features whose weight is in megabyte
> `coordinates` arrays, and this is tens of thousands of features whose
> `coordinates` is three numbers and whose weight is in flat scalar
> `properties`. **If the probe describes them the same way, that is a finding**;
> I expect it to describe them very differently, and prediction 7 says so.

**Not chosen to stress anything repaired today.** GeoJSON has fixed field names
throughout, so I expect `folds()` silent and defect 25's back-reference to fire
zero or one times — the same honest near-zero expectation file 24 recorded and
met.

## What this file disconfirmed

**Defect 26 — three fields are LISTS PACKED INTO STRINGS and the probe says
nothing.** Recorded, not repaired, per rule 5.

```
$.features[].properties.types      ,nearby-cities,origin,phase-data,
$.features[].properties.ids        ,nc75415572,
$.features[].properties.sources    ,nc,
```

All 10,885 records carry all three. **`an item of features 10,885 rows x 30
cols` hands a reader a `types` column that is really a list**, which is item
20's list-column problem wearing a disguise — god's spec refuses a list-column,
and this one would pass as text.

### It is structurally detectable, and the measurement includes the false positive

Measured over every text field in all 25 documents, with no word list:

| rule | fields matched | true | false |
|---|---|---|---|
| wrapped in a non-alphanumeric char **and that char appears >2 times** | **1** | `types` | **0** |
| wrapped in a non-alphanumeric char, nothing else | **4** | `types`, `ids`, `sources` | **1** — `04-gharchive`'s `emoji` = `:hash:` |

**The strict rule is exact and misses two thirds of the case. The relaxed rule is
complete here and cannot tell a one-element list from a wrapped token**, because
`,nc,` and `:hash:` are structurally identical — a delimiter at each end and
nothing between. That is not a threshold that needs tuning; it is a genuine
ambiguity in a single value.

> **What resolves it is the document, not the field.** `types` proves the
> convention with interior delimiters, and `ids` and `sources` are siblings on
> the same records using the same character. **Sibling fields sharing a wrapping
> character is the evidence**, and no single field carries it. That is the same
> shape of argument as item 15 — *the discriminator is outside the record*.

**It makes no existing number wrong, so like defect 18 it is a report and not a
repair.** The probe calls `types` text, and it is text.

## The fourteenth tool, 2026-08-11 — `try-tidyr.R`

**tidyr is the only one of the fourteen with a verb for defect 26's packed
lists.** Three fields are lists packed into strings — `types` is
`,nearby-cities,origin,phase-data,` with sentinel commas at both ends, holding
1 to 13 items once they are stripped.

```r
separate_longer_delim(types, delim = ",")   # -> 27,762 rows, 21 type names
```

`origin` 10,885 · `phase-data` 10,881 · `nearby-cities` 3,298 · `scitech-link`
1,077 · `focal-mechanism` 607.

> **It does NOT detect the packing.** A person had to see the commas and name
> the delimiter. **Defect 26 is about DETECTION and stands exactly as written**;
> what changes is that the repair needs no new verb.

**GeoJSON's coordinates are the opposite case and the clean statement of a
limit.** `coordinates` is `[lon, lat, depth]` with no names anywhere in the
document, so `unnest_wider` can only invent `coordinates_1`, `_2`, `_3`.
`17-openlibrary` showed the same package zipping two parallel arrays correctly —
**the difference is that there the names lived in a sibling array and here they
live in the GeoJSON specification. No tool recovers names that are not in the
bytes.**

**The largest wrong row count in the fourteen files, by a wide margin.**
`unnest_longer(properties)` returns **283,010 rows from 10,885 features**,
because `properties` is an object with 26 fields.
