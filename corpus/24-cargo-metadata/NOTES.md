### 1. The typing destroys the evidence the probe judged on

The probe calls `$.packages[].features` **KEYS THAT ARE DATA**: 28 Cargo feature
names over 8 packages, **23 appearing exactly once**. That once-only share is
what `classify()` reads as an open vocabulary.

**DuckDB types it a STRUCT, and a STRUCT has every field on every row:**

| | names | occurrences | appearing once |
|---|---|---|---|
| through the TYPED column | 28 | **224** | **0** |
| through the RAW JSON | 28 | **40** | **23** |

> **One tool, two routes, and only the second can see the property the verdict
> rests on.** The open vocabulary was not lost in the answer — **it was lost in
> the schema.** `224` is `28 × 8`: every package now carries every feature name.

**And DuckDB chose STRUCT, not MAP.** Entry 20 found it choosing MAP for
`variations` and STRUCT for `bottle.stable.files`, two structurally identical
sites. Adding this one makes **three keyed collections across two documents and
two verdicts with no rule between them** — so the MAP/STRUCT choice does not
track keys-as-data.

### 2. Question 6 splits the thirteen into three groups, cleanly

| | what they do with the 28 feature names |
|---|---|
| **pandas, polars, jsonlite, DuckDB** | build them into a **SCHEMA** — 28 columns, or 28 struct fields |
| **tidyjson, rrapply** | put them in a **COLUMN** (`gather_object`, `melt`) — the right shape |
| **jq, jqr, ijson, glom, pydash, purrr, jmespath** | leave them as keys and supply the ingredients |

**Only the middle group's output survives the next file.** `cargo add` changes

## The fourteenth tool, 2026-08-11 — `try-tidyr.R`

**tidyr is in TWO of question 6's three groups at once, and the user picks:**

| | |
|---|---|
| `unnest_wider(features)` | **8 x 29** — the 28 feature names become COLUMNS, and `cargo add` invalidates the header |
| `unnest_longer(features, indices_to =)` | **40 x 3** — the names become DATA, and it survives |

**No other tool in this comparison offers the choice as a named pair.** The long
answer reports the RAW-JSON figures — **40 occurrences with 23 names appearing
once** — which is exactly the evidence DuckDB's STRUCT destroyed.

**`unnest_auto` picks the survivor, and the reason is not the vocabulary.** It
says *"elements are named, but have no names in common"* — and the intersection
is empty because **`fathom-cli` and `fathom-core` have ZERO features**, not
because 23 of 28 names occur once. `default` is on 5 of 8 packages; **drop the
three that lack it and the same call says "1 names in common" and builds the
29-column schema.**

> **The rule is an INTERSECTION and the probe's is a RATE.** Any single shared
> name flips it, so on this document the right answer is bought by two packages
> happening to have no features at all.
>
> **And `16-movie-ratings` settles what that is worth.** Same empty
> intersection, same decision to melt — and there the melted keys are ordinary
> field names and the answer is WRONG, while the real keys-as-data are
> discarded. **One rule, two documents, opposite correctness: this entry's
> success was luck rather than measurement.**
